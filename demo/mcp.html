MCP server

Connect a local agent to Gumroad Merchant

The dashboard is one interface for the prototype. MCP is the second one: a local agent can call the same Gumroad Merchant tools from Codex, Claude, Cursor, or another MCP-capable workspace.

Admin API/CLI Context

I moved the issue-specific admin API/CLI framing here because it is really an agent-surface question, not the main browser dashboard story. Gumroad issue #4677 asks how admin functionality could be exposed through an API and/or CLI, and MCP is the cleanest place to show that direction without turning the browser demo into an admin tool.

MCP makes sense for this prototype because the Gumroad Merchant agent is already built around explicit calls, routing, and safety boundaries inside the web UI. The same workflow layer can move into an MCP server, so a creator or internal operator can talk to Gumroad Merchant through their own local agent setup, their choice of agent provider, their preferred LLM provider, or whatever AI application they already use.

In that setup, the local agent can inspect the tool contract, preview the action shape, choose the right execution mode, and keep sensitive writes gated. The browser dashboard stays focused on creator-facing review workflows; this MCP tab carries the admin API/CLI exploration.

  • Prioritize exact user and purchase lookup before sensitive writes.
  • Use short-lived scoped admin tokens from existing admin identity.
  • Keep internal admin APIs separate from the public v2 API surface.
  • Expose reviewable commands through an internal CLI shape, not browser cookies or static API keys.
  • Use Gumroad Merchant MCP as the local seeded harness for that contract.

Overview

The MCP path takes the Gumroad Merchant buildout from the web UI and exposes the same calls through a local stdio server. The agent still uses explicit tool names, bounded inputs, seeded data, and clear execution modes. The important change is that the creator can talk to Gumroad Merchant from the agent environment they already use.

1. Copy the installer prompt

Open the Installer Prompt tab and copy the full prompt into the MCP-capable agent you want to configure.

2. Let the agent inspect its host

The prompt tells the receiving agent to detect Codex, Claude, Cursor, or another MCP host before editing config.

3. Add the local server command

The MCP command is the repo launcher script, not a cloud URL or production Gumroad credential.

4. Ask for the help menu

After reload, ask: "Use Gumroad Merchant to show me what I can do." The server returns tools, prompts, parameters, and safety boundaries.

Manual Config

If you want to wire it by hand, point your MCP host at the launcher inside this project checkout. Replace <PROJECT_ROOT> with the absolute path to the repo folder on your machine. 

<PROJECT_ROOT>/scripts/gumroad-merchant-mcp.sh

The config shape depends on the agent host. In TOML-style hosts, the entry should look like this: 

[mcp_servers.gumroad_merchant]
	command = "<PROJECT_ROOT>/scripts/gumroad-merchant-mcp.sh"

Safety Protocol

  • The local demo runs in GUMROAD_MERCHANT_MODE=seeded.
  • It uses local seeded demo data and a local Gumroad help-doc corpus.
  • It does not call Gumroad production services or read creator records.
  • Seeded demo actions return review_only: true and will_execute: false when they would affect a real Gumroad account.
  • Local write tools can only write test-profile rows or generated artifacts inside this repo.
  • The production MCP direction is scoped read-write automation, not a permanent read-only wall: low-risk reads can run directly, while sensitive writes need scoped auth, preflight checks, confirmation, and audit logs.

MCP Merchant automation

Review-only is the boundary for this seeded demo, not the ceiling for the MCP server. MCP is where Gumroad Merchant should become a real automation surface: the same calls and routing from the web UI, exposed to Codex, Claude, Cursor, or another agent a creator already uses.

User UI Permission Controls

I would add an MCP section inside the Gumroad user settings where a creator controls what their local agent can read, draft, and execute. Monthly sales, customer lookup, product catalog, refunds, disputes, emails, posts, pricing, subscriptions, and payouts should each have their own access level. That gives the agent enough permission to run the business, while the creator still decides which activities are read-only, which can stage a draft, and which are allowed to execute after confirmation.

Read the business

Monthly sales, product catalog, refunds, disputes, subscriptions, payout state, and customer history as exact tool calls instead of dashboard hunting.

Run merchant workflows

Draft and eventually execute refunds, dispute packets, buyer emails, posts, product edits, pricing updates, and subscription changes with the agent carrying context forward.

Gate real writes

Use dry-run, confirm, and apply modes so the agent can explain the action before it touches money, access, pricing, payouts, or customer communication.

Keep an audit trail

Every write should return the affected object, requested change, risk level, confirmation state, idempotency key, and audit note.

Planned Read-write Surface

  • Monthly sales, product catalog, customer lookup, purchase lookup, refund history, dispute status, payout state, and subscription health.
  • Refund drafts and refund execution with eligibility checks, amount validation, reason capture, and merchant confirmation.
  • Dispute workflows that gather evidence, summarize the response, stage attachments, and submit only after confirmation.
  • Emails, receipts, posts, and product announcements with preview, recipient checks, and send confirmation.
  • Product listing edits, pricing changes, file or content updates, subscription changes, and payout holds/resumes behind role checks and audit logging.

Execution Model

  • Default reads are direct and high-signal, so the agent can summarize the business without asking the creator to navigate a dashboard.
  • Write tools expose `dry_run`, `confirm`, and `apply` modes instead of a single dangerous button.
  • Production writes require scoped tokens, role checks, preflight validation, idempotency keys, and durable audit notes.
  • High-risk writes, like payouts, pricing, mass email, subscription access, and refunds, require explicit confirmation with the exact object and effect shown first.
  • The current seeded MCP harness proves the contract locally; the production path connects the same contract to real Gumroad merchant APIs.

Command List

After the MCP server is connected, these are the kinds of plain language commands a creator could ask their agent to run. The agent handles the tool calls and brings back the answer, draft, or next safe action.

Open the help menu

Start here when you want the agent to show the available Gumroad Merchant tools and permission state.

Use Gumroad Merchant to show me what I can do.
Summarize the business

Pull the important revenue, conversion, refund, traffic, and churn context into one short readout.

Use Gumroad Merchant to summarize monthly sales and tell me what changed.
Check product listings

Ask for product-page status, files, pricing, and metadata without clicking through every listing.

Use Gumroad Merchant to review my product catalog and flag any listing that needs an update.
Review refunds

Have the agent find the highest-risk refund case and explain the safest next step.

Use Gumroad Merchant to review refund risk and draft the next action.
Build a dispute packet

Collect the evidence, timeline, buyer context, and response draft for a chargeback workflow.

Use Gumroad Merchant to build a dispute packet for the highest-risk case.
Draft customer communication

Create a buyer email or receipt resend draft while keeping send permission separate.

Use Gumroad Merchant to draft a buyer reply for the refund case that needs attention.
Plan growth work

Turn current product and traffic signals into a campaign, post, or launch plan.

Use Gumroad Merchant to build a marketing plan for the product with the biggest opportunity.
Preview a write action

Show the exact object, risk, confirmation state, and audit note before any write is allowed.

Use Gumroad Merchant to dry-run a pricing update and show me what would change.
