Gumroad Merchant Chat Durability

Gumroad Merchant durability plan: SQL stores the transcript of record, Redis coordinates short-lived in-flight state, and Temporal can run 24-hour agent workflows, retries, and long jobs across refreshes or later sessions.

Click pink hotspots to drill in

SQL is durable memory

  • User row is inserted before the agent runs.
  • Assistant row is appended after tools/model finish.
  • Saved chats, audit notes, citations, and statuses need database semantics.

Redis is runtime memory

  • Stores request locks, dedup keys, rate limits, and current message hints.
  • Can cache the last few messages for speed.
  • If Redis is stale or gone, SQL reload still works.

Temporal owns long work

  • Production target for long agent runs and retries.
  • Workflow can resume after worker crashes.
  • UI can show received/processing/completed from SQL while work continues.

Illustrated explainer layer

The core idea

The chat transcript is product data, so it goes in SQL. Redis only carries short-lived operational state. Temporal is the production runner that keeps long work durable even when HTTP requests, browsers, or workers fail.

SQL = memory of record | Redis = runtime coordination | Temporal = durable execution
  1. Persist the user message with status received.
  2. Set Redis in-flight metadata with request_id and user_message_id.
  3. Run the agent through a Temporal workflow in production.
  4. Append assistant output and citations to SQL.
  5. Clear Redis lock and let reloads rebuild from SQL.

API write order

Save first, run second

The important change is that the API does not wait for the model before writing the user's text. It inserts the message immediately with status received, then starts the runtime work. If the model call fails, the user's input still exists and can be retried, inspected, or shown as failed.

POST /api/agent/chat -> INSERT user message -> Redis in-flight -> agent/workflow -> INSERT assistant message
  • Prevents lost prompts during model errors or server crashes.
  • Gives the UI a real status to render during processing.
  • Creates an audit-friendly trail for support/refund/admin conversations.

SQL durability

The transcript needs database semantics

A support, refund, or admin conversation can become evidence. That means it needs stable IDs, timestamps, statuses, citations, actor information, and audit notes. SQL is the right place for that record.

chat_messages(id, session_id, role, status, content, citations_json, metadata_json, created_at)
  • Saved conversations should survive Redis eviction and deploy restarts.
  • Audit notes and dispute evidence should be queryable later.
  • Message status lets the UI distinguish received, completed, and failed states.

Redis runtime cache

Redis can speed up session state, but it should not own history

Redis can cache the current message, the last few messages, or an in-flight marker. It can also store request_id and user_message_id so the app can compare Redis state against SQL. But if Redis and SQL disagree, SQL is the authority.

gumroad-merchant:inflight:{session}:{message_hash} -> { request_id, user_message_id, product_id, date_range }
  • Good for duplicate prevention and rate limiting.
  • Good for fast current-session hints after refresh.
  • Bad as the only store for transcripts or audit history.

Temporal production target

Temporal should own long-running agent execution

The current local demo runs the agent synchronously in FastAPI. Production should hand the accepted message to a Temporal workflow. Temporal can retry tool activities, survive worker restarts, and keep the workflow status available while the browser comes and goes.

workflow_id = merchant_chat:{session_id}:{request_id}
  • FastAPI returns accepted or streams progress instead of owning the whole run.
  • Workers run agent/tool activities and write final state to SQL.
  • Retries happen around activities, not by duplicating user messages.

Reload behavior

On reload, rebuild from SQL and enrich from Redis when available

The browser only needs a session_id. On reload, the API loads the transcript from SQL. If Redis still has an in-flight lock or last-message cache, the UI can show processing immediately. If Redis has expired, SQL still shows the durable user message and its status.

GET /api/agent/chat/history?session_id=... -> SQL transcript -> optional Redis in-flight hint
  1. Load session_id from browser storage.
  2. Read chat_messages from SQL.
  3. Check Redis for active request metadata.
  4. Render received/processing/completed based on durable state.
